PART ONE：用 Python + GitHub Actions 搭建自动化数据看板

分享了三个看板的制作过程：A股风格轮动盯盘、中证红利定投指示板、纳斯达克100定投指示板。 三个看板共用同一套技术栈，从零搭建到全自动运行，这里总结一下通用的方法论和容易踩的坑。

🎯 三个看板各自的目标：
  1. 关注风格轮动和市场场景切换
  2. 定投纳指

二、通用架构：三板斧流水线

每个看板都是 三步走，无一例外：

CSV 落盘  →  JSON 落盘  →  HTML + JS 落盘

每一步都是纯 Python 脚本，输入是文件，输出也是文件。没有任何数据库、没有后端 API、没有 Docker。极简，极其好维护。

2.1 第一步：数据抓取（fetch_data.py）

核心问题只有一个：从哪拿数据？

看板数据内容数据源Python 库
A股盯盘风格指数 + 宽基指数 + ETF份额新浪财经 / 腾讯财经 / tushareakshare
中证红利000922价格 + PE-TTM新浪财经akshare
NDX定投纳斯达克100 + VIX + CNN恐慌贪婪Yahoo Finance + CNNyfinance + requests
✅ 心得：数据源一定要有多级兜底。
A股数据商发布时间不一致：新浪约 16:00 就有当日数据（快但偶尔缺），腾讯约 16:30-17:00（慢但全），tushare 需要 token 但最快。代码里做了三级降级：

tushare（有 token 则优先） → 新浪（快） → 腾讯（兜底）

而且还有一个巧妙的检查：如果新浪返回的最新日期不是今天，自动切到腾讯补数据。
⚠️ NDX 的数据源特别坑：Yahoo Finance 的历史数据接口经常抽风，有时候返回空，有时候延迟一天。所以 GitHub Actions 里做了 3 次重试 + 30 秒间隔，并且在 cron 里安排了三个时间点兜底（北京时间 6:30 / 8:30 / 12:00）。

2.2 第二步：信号计算（gen_data.py）

数据拿到之后，要做的事情就是把原始价格变成"信号"。

A股盯盘的信号体系：

  • 均线系统：MA20 / MA60 / MA120 / MA250，判断指数处于什么位置
  • 破位计数：跌破几条均线 + 回撤幅度 + 均线死叉 → 得到 0~10 的分数
  • 仓位评级：GREEN 牛市 YELLOW 调整 ORANGE 中期走弱 RED 熊市
  • 国家队ETF监控：从 ETF 份额变动推算净申购金额，结合比率判断"托底"还是"减速"
  • 风格轮动：60日最强/最弱风格、价值/成长比率、大小盘轮动

定投看板的信号体系：

  • 核心模型：MA200 分位值。多种模型对比（单指标 vs 复合打分法）后，从收益率、回撤控制、定投节奏、可理解性多维度评价，选择了这个最符合需求的指标
  • 计算 当前价格 / MA200，在历史上处于什么分位。分位越低 → 越低估 → 投更多
  • 分位值 → 分数 → 倍数映射
✅ 心得：信号逻辑要"自解释"。比如定投金额的计算公式直接在页面上显示出来，用户不需要看代码就能理解为什么是这个数。

2.3 第三步：页面生成（build_html.py）

reasonix + GitHub Desktop 自己搞定，我只做评价和测试。

这一步是整个方案最"务实"的选择：不用任何前端框架，直接把数据写进 HTML。

  1. Python 读取 dashboard_data.json
  2. 用 json.dumps() 把数据写成 const DATA = {...} 塞进一个 .js 文件
  3. HTML 通过 <script src="dashboard_data.js"> 加载数据
  4. 页面渲染全部用原生 JavaScript + Chart.js（CDN 引入，零依赖安装）
🤔 为什么不用 React/Vue？
因为这个场景只有一个静态页面，前端框架的构建链（webpack/vite/npm install）完全是负资产。纯 HTML + 原生 JS 的好处：
✅ 浏览器直接打开就能看（python -m http.server 一键本地调试）
✅ GitHub Pages 原生支持，零配置
✅ 任何人都能看懂、修改，不需要前端背景

Chart.js 画图非常简单，比如画上证指数 + 均线：

new Chart(document.getElementById('chartSH'), {

      { label: 'MA250', data: Array(180).fill(DATA.ma250), borderDash: [6,3], ... },
    ]
  }

三、全自动运行：GitHub Actions + GitHub Pages

我的需求是能够定期自动更新，但没有实时的诉求所以不用特别高频。
（根据使用场景和需求来，但也很容易出错，需要多用多校验）

这是最关键的一步——让看板自己更新，不需要人操作。

3.1 定时触发

在 .github/workflows/ 下放一个 YAML 文件：

on:
  schedule:
    - cron: '0 0-11 * * 1-5'   # 北京时间 8:00-19:00，每小时一次，周一到周五
  workflow_dispatch:             # 手动触发按钮
⚠️ 坑：GitHub Actions 的 cron 是 UTC 时间！
北京时间 = UTC + 8。所以 0 0 是北京时间早上 8 点，0 11 是北京时间晚上 7 点。写反了就会在半夜跑。

3.2 执行流程

steps:
  - checkout 代码
  - 安装 Python + pip install 依赖
  - python fetch_data.py    # 抓数据 → CSV
  - python gen_data.py      # 算信号 → JSON
  - python build_html.py    # 拼页面 → HTML
  - git commit + git push   # 推回仓库

整个流程跑完大约 2-3 分钟。A股看板用了每小时更新（覆盖盘中到收盘后），NDX 用了早间三次兜底。

3.3 GitHub Pages 自动部署

只要仓库设置里开启 GitHub Pages，指向 main 分支的根目录，每次 Action push 新的 HTML 后，GitHub Pages 会自动重新部署。一般 1-2 分钟内生效。

⚠️ 坑：浏览器缓存。页面更新了但看到的还是旧的。解决方案：
✅ HTML 里加 <meta http-equiv="Cache-Control" content="no-cache">
✅ JS 引用加版本号参数：<script src="dashboard_data.js?v=20260731120000"></script>
✅ 更进一步：搞了一个 version.json，页面每 5 分钟轮询一次，检测到版本变化自动刷新

3.4 版本自动检测刷新

// 每 5 分钟检查 version.json 是否变了
function checkVersion() {
  fetch('version.json?t=' + Date.now(), { cache: 'no-store' })
    .then(r => r.json())
    .then(v => {
      if (v.version !== localStorage.getItem('last_version')) {
        localStorage.setItem('last_version', v.version);
        showToast('🆕 数据已更新，刷新中...', 'success');
        setTimeout(() => location.reload(), 1000);
      }
    });
}
setInterval(checkVersion, 5 * 60 * 1000);

这样你打开页面放在那里，数据更新了会自动刷新，不用手动 F5。

四、最容易踩的 8 个坑

🕳️ 坑 1：数据源的时间差
A股数据商不是收盘立刻就有数据的。新浪大约 16:00，腾讯 16:30-17:00。如果你 15:30 拉数据，拿到的是昨天的。
对策：多数据源降级 + 检查最新日期是否为今天 + 错开 cron 时间。
🕳️ 坑 2：PE-TTM 数据经常空
akshare 获取中证红利 PE 的接口有时候返回空或报错。
对策：PE 失败不要阻断整个流程，用 try/except 包起来，PE 缺失时页面显示 "N/A"，其他功能照常。
🕳️ 坑 3：MA200 需要足够的历史数据
ndx.rolling(200).mean() 要求至少有 200 个交易日（约 10 个月）的数据。如果数据文件是新拉的，前 199 天全是 NaN。
对策：确保 fetch 脚本拉取至少 2-3 年的历史数据，start='20200101' 起步。
🕳️ 坑 4：GitHub Actions 的磁盘和内存限制
免费版 Actions 的 runner 只有 7GB RAM + 14GB SSD。akshare 拉全量 A股历史数据大约几百 MB，完全够用。但如果要跑回测或大量计算，注意 timeout-minutes 设置（默认 360 分钟，够用）。
🕳️ 坑 5：git push 冲突
如果两个 cron 同时触发（比如 A股的和 NDX 的都写同一个文件），会 push 冲突。
对策：使用 concurrency 限制并发 + push 前先 git pull --rebase，失败后重试 3 次。
🕳️ 坑 6：ffill 导致的"假数据"
如果某天数据缺失，pandas.fillna(method='ffill') 会自动用前一天的数据填充（容易给人造成误解，所以测试要细致）。这会导致你以为有最新数据，其实是旧的。
对策：在 gen_data.py 里检查最新行是否实质更新： 
# 检查不完整数据
unchanged = [n for n in style_names if abs(last[n] - prev[n]) < 0.001]
if len(unchanged) >= 3:
    df_final = df_final.iloc[:-1]  # 丢弃
🕳️ 坑 7：周度定投的 ISO Week 对齐
定投按周执行，但不同数据源对"周"的定义可能不一致。必须用 isocalendar() 的 (year, week_number) 来判断是否是同一周。每周选最后一个交易日执行，如果那周没交易（节假日），顺延到下一个交易日。

五、方法论总结：从零搭建一个看板的 SOP

其实 DS 自己都可以搞定，我的任务是提示词要够细致准确的让 AI 明白到底需要他做什么——包括目标、准确描述现象、实现前先讨论方案、总结落地、不断根据需求迭代。
  1. 确定数据源 → 找到能稳定拉数据的 Python 库（akshare / yfinance / requests）
  2. 写 fetch 脚本 → 拉数据 → 存 CSV，做好多源兜底和错误处理
  3. 写 gen_data 脚本 → 读 CSV → 用 Pandas 算指标 → 输出 JSON
  4. 写 build_html 脚本 → 读 JSON → 拼 HTML + Chart.js → 输出纯静态页面
  5. 本地调通 → python -m http.server 8765 打开浏览器看效果
  6. 扔到 GitHub → 配 Actions cron → 设 GitHub Pages → 完事
  7. 加版本轮询 → version.json + 前端轮询 → 打开页面自动刷新
⏱️ 整个周期：如果数据源明确、指标公式清楚，一个看板从零到全自动上线大约 2-4 小时。第一个最慢（搭架子），第二个第三个就是复制粘贴改参数。

PART TWO：使用各种 AI 后的心得体会

AI 都能做什么

✅ 能做❌ 不能做
信息整理 — 多源数据汇总、关键指标监控、异常信号标注 🚫 预测价格 — AI能分析趋势，但无法预测明天涨跌
逻辑推演 — 数据间关联分析、历史规律归纳 🚫 替代判断 — AI没有你的负债表、现金流、家庭责任
纪律守门 — 设定规则的自动提醒、情绪化操作预警 🚫 消除不确定性 — 只能让你更清楚看到不确定性，不能消灭它
记忆外接 — 你的判断记录、历史决策复盘、教训归档
🔑 核心认知：AI是放大镜，不是方向盘——它让你看得更清楚，但车往哪开、开多快、什么时候刹车——必须是你自己决定。

哪里容易出错

❌ 错误流程：
你："我该买什么？" → AI："建议关注XX..." → 你：（无脑跟单）
✅ 正确姿势：idea先行，然后动起来，多比较

你："我觉得XX方向长期逻辑成立"
AI："支持该观点的3个数据... 可能推翻的2个风险..."
你："逻辑对，但短期过热，等回调5%"
AI："已设定提醒，条件满足时通知你"

升级版：第一性原理 + 子 agent 相互 PK —— 人提假设，AI验证；人定策略，AI监控。
